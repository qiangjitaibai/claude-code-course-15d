第 1 天 · 启动与第一段对话：Claude Code 到底怎么用

5月7日 周三Day 1/15

你已经装好了 Claude Code。打开终端，进入你的项目目录，输入：

claude

回车。一个蓝色终端界面（TUI）出现。没有侧边栏、没有设置面板，就是一个对话窗口。

界面速览

  • 上方：对话历史区域，滚动查看你和 Claude 的每一句话
  • 下方：输入区，你打字的地方
  • 左上角：当前模型名称和会话标识
  • 按 Esc 可以退出输入模式，用方向键浏览历史消息

    • 所有操作通过打字或斜杠命令完成。简洁到极致。

    启动参数：进入项目的方式不止一种

    # 基础启动
claude

# 指定模型启动（跳过模型选择菜单）
claude --model sonnet
claude --model opus

# 恢复上一次会话（不用重新解释项目背景）
claude --resume
# 或启动后在对话里说「继续上次的对话」

# 打印模式：不进入 TUI，一次性执行完成后输出结果并退出
claude -p "这个项目的入口文件是哪个？"
claude -p "帮我修复 src/utils/auth.ts 里的所有类型错误"

# 从 stdin 传入内容（适合管道场景）
cat error.log | claude -p "分析这些报错，告诉我怎么修"
git diff HEAD~3 | claude -p "审查这些改动，总结主要变更"

# 指定工作目录
claude --cwd ~/projects/my-app

    -p 打印模式是自动化脚本里的利器——比如在 CI 里让 Claude 分析构建报错，输出结果直接写入日志。

    第一条消息发什么

    不要上来就说「帮我写一个网站」。Claude Code 需要先理解你的项目：

    帮我看看这个项目的结构，告诉我它是什么、怎么组织的

    Claude 会自动读取文件结构、package.json、README，给你一个项目概览。相当于新人入职第一天先看一眼代码库再干活。

    进阶版第一条消息：

    仔细读一遍这个项目的代码，然后回答：
1. 项目的核心功能是什么
2. 技术栈是什么（框架、数据库、关键依赖）
3. 代码的目录组织逻辑是什么
4. 有没有明显的不合理设计
5. 如果我接下来要开发新功能，入口在哪里

    这个 prompt 让 Claude 不仅「看一遍」，还做一次迷你代码审查。你会得到一个比 README 还准确的项目地图。

    斜杠命令完整指南

    输入 / 弹出命令菜单。按使用频率排序：

    命令作用频率
    `/help`列出所有命令偶尔
    `/clear`清空对话历史日常
    `/cost`查看会话花费（token 数和金额）日常
    `/doctor`诊断 Claude Code 配置问题出问题时
    `/init`初始化项目的 CLAUDE.md新项目
    `/compact`压缩上下文，Claude 把历史总结成摘要后继续长篇会话
    `/status`查看令牌使用量、上下文窗口占用率时不时
    `/config`打开配置文件调配置时
    `/bug`提交 Claude Code 本身的 bug 报告很少
    `/pr-comments`查看当前会话中 Claude 写过的 PR 评论GitHub 协作时

    高阶技巧：/compact 什么时候用

    当你发现 Claude 回复变慢、或者它开始忘记你前面说的话，说明上下文窗口快满了。此时输入 /compact，Claude 会把整个对话历史压缩成一个结构化摘要，释放空间继续干活。比 /clear 好——不会丢信息。

    高阶技巧：-p 模式 + shell 管道实战

    # 用 Claude 审查你的代码改动
git diff main | claude -p "审查这段 diff。指出：1. 潜在 bug 2. 性能问题 3. 命名建议"

# 用 Claude 写 commit message
git diff --staged | claude -p "基于这个 diff 生成一个 conventional commits 格式的 commit message"

# 用 Claude 分析日志
journalctl -u myapp --since "1 hour ago" | claude -p "分析日志，找出异常模式，按严重程度排序"

    三个最重要的操作习惯

    1. 先让它看，再让它做。 给它上下文，它会聪明十倍。
    2. 一次说一件事。 「顺便也」是效率杀手。拆成多轮对话。
    3. 看 diff。 Claude 每次编辑文件后会显示差异对比。花 5 秒扫一眼，你不看就没人帮你看。
    4. （新加）让它解释自己做了什么。 重要操作后加一句「解释一下你为什么这样改」，理解它的思路，你也在学习。

    常见踩坑

    坑 1：Claude 改了不该改的文件

    你说「优化这个函数」，Claude 可能顺便把同一个文件里其他函数也改了。修复方法：明确说「只改这个函数，不要碰文件里其他代码」。

    坑 2：Claude 的修改破坏了别的地方

    你改了 A 文件的函数签名，但 B 文件还在用旧的。修复方法：加一句「改完后检查所有调用处，确保兼容」。

    坑 3：上下文丢得太快

    你跟 Claude 聊了 50 轮，忽然让它处理一个不相关的新任务——它被旧上下文干扰。修复方法：新任务前先用 /compact 或 /clear。

    今天的小练习

    # 1. 用 -p 模式快速分析项目
claude -p "看看这个项目，用三句话总结它"

# 2. 启动 TUI 模式，用扩展版第一条消息让 Claude 做完整分析
# （上面那个5条问题的版本）

# 3. 输入 /cost 看看花了多少
# 4. 输入 /status 看看上下文占用
# 5. 试试管道模式：把 git diff 喂给 Claude

    今日小结： Claude Code 不是搜索引擎，是能读懂你代码库的配对程序员。TUI 和 -p 两种模式覆盖交互和自动化两种场景。你的核心任务：给它上下文。

第 2 天 · 读代码：让 Claude 成为你的代码导航仪

5月8日 周四Day 2/15

很多开发者打开 Claude Code 第一反应是「帮我写个功能」——等价于第一次去健身房就杠铃深蹲。先学会看，再学会写。

六个提问模式（含高阶变体）

模式 1：定位型

用户登录的逻辑在哪里实现的？带我去看。

高阶变体：

跟踪一下这个项目的请求生命周期：
1. HTTP 请求进来后经过了哪些中间件？
2. 路由分发在哪一层？
3. 业务逻辑在哪一层？
4. 数据库查询在哪一层？
给每一步标上文件名和行号。

模式 2：解释型

逐行解释 src/services/payment.ts 里的 processRefund 函数，
特别是那段 Promise.all 的逻辑——为什么要用 Promise.all？

高阶变体：

用「一个完全没有编程经验的 PM」能听懂的语言，
解释这段代码在做什么。不要用任何术语。

这个方法出奇地有用——如果你能用 PM 语言讲清楚，说明你自己也真懂了。如果 Claude 讲不清楚，说明这段代码设计本身就有问题。

模式 3：追踪型

找出所有调用 validateToken 的地方，画出调用链。
如果 validateToken 抛出异常，每个调用处会怎么处理？

高阶变体：

做一次「死亡路径分析」：
如果这个 API 调用第三方服务超时了，
1. 错误会怎样一层层传播？
2. 最终用户会看到什么？
3. 有没有哪一层吞掉了错误？

模式 4：对比型

src/services/ 下有两个文件 auth-v1.ts 和 auth-v2.ts。
它们有什么区别？能合并吗？合并的风险是什么？

模式 5：安全审查型（新增）

审查 src/api/ 下所有接口的安全性：
1. 哪些接口没有鉴权？
2. 有没有 SQL 注入风险？
3. 用户输入有没有被校验和清洗？
4. 是否有敏感信息泄漏到日志或错误消息里？

模式 6：性能审查型（新增）

分析 src/services/order.ts 里 createOrder 函数的性能问题。
重点关注：
1. 有没有 N+1 查询？
2. 循环里有没有数据库操作？
3. 有没有可以并行的操作被串行执行了？
4. 缓存机会在哪里？

@ 引用的高级用法

# 引用文件
@src/utils/auth.ts — 解释这个文件的设计

# 引用目录（Claude 会分析整个目录结构）
@src/api/ — 这个目录下所有接口有没有重复的逻辑？

# 引用多个文件做交叉分析
@src/models/User.ts @src/services/userService.ts —
这两个文件的职责边界清楚吗？

# 在一个 prompt 里引用多个信息源
@src/types/order.ts 定义了 Order 接口，
@src/services/payment.ts 使用了 Order，
但 @src/api/orders.ts 里返回的格式和 Order 不一致——
帮我找出来，修复。

让 Claude 画出结构

# ER 图
帮我画出这个项目的数据库模型关系图（用 Mermaid 格式）

# 依赖图
画出 src/ 下所有模块之间的依赖关系图，标出循环依赖

# 数据流图
画出用户注册功能的完整数据流：
从前端表单 → API → Service → 数据库 → 邮件发送

# 状态机
用户订单的状态转换：待支付→已支付→发货中→已签收→已完成。
画出状态机图，包括哪些状态可以回退

高阶读码技巧

技巧 1：让 Claude 当你的 onboarding 导师

我是一个新加入团队的开发者。这个项目的代码是
一个 3 年积累下来的 NestJS 项目。帮我写一份
「新人 30 分钟上手指南」：
1. 最重要的 5 个文件（列出并解释）
2. 核心业务逻辑流程图
3. 最危险的操作（改了会出事的地方）
4. 本地开发环境搭建步骤

技巧 2：逆向理解遗留代码

这个文件 src/legacy/reportGenerator.ts 有 800 行，
没有任何注释，原始作者已经离职。帮我：
1. 拆成逻辑段（每段起个名字）
2. 画出输入→输出的数据流
3. 找出所有 hardcode 的配置值
4. 标记你觉得可删的 dead code

技巧 3：生成文档

给 src/services/ 下所有 public 方法生成 JSDoc 注释，
但不要改代码逻辑，只加注释。格式：
- @param 描述每个参数
- @returns 描述返回值
- @throws 描述可能抛出的异常
- @example 给一个使用示例

今天的小练习

  1. 用「PM 语言」让 Claude 解释你项目里最复杂的那个函数
  2. 做一次「死亡路径分析」——找一个 API，让 Claude 画出所有异常路径
  3. 让 Claude 生成你项目的 Mermaid ER 图
  4. 试试多文件引用：@fileA @fileB 让 Claude 找出不一致的地方

今日小结： 读代码不只是让 Claude 帮你找文件——它是你的代码考古学家、安全审计师、性能顾问、和新人导师。70% 时间在读数，学会问，才是真功夫。

第 3 天 · 写代码：从一行到一整个文件

5月9日 周五Day 3/15

读了两天，开始写。别一上来就让 Claude 写一千行——从一行开始。

修改现有代码

# 基础：重命名
把这个函数名从 getUser 改成 fetchUserById，
更新所有调用它的地方，包括测试文件里的引用。

# 进阶：重构函数签名
把 createOrder(userId, items, callback) 改成
createOrder({ userId, items, onSuccess, onError })，
使用对象参数而不是位置参数，更新所有调用处。

# 实战：加功能
给 src/api/products.ts 的 GET /products 接口加三个查询参数：
- category?: string — 按分类过滤
- minPrice?: number — 最低价格
- sort?: 'price_asc' | 'price_desc' | 'newest' — 排序方式
同时更新 TypeScript 类型定义和参数校验逻辑。

从零创建文件：五个实战例子

# 例子 1：工具函数
创建 src/utils/retry.ts：
- retry(fn, options) 函数，自动重试失败的异步操作
- options.maxRetries 默认 3
- options.delay 默认 1000ms，每次重试翻倍（指数退避）
- 如果全部失败，抛出原始错误

# 例子 2：React 组件
创建 src/components/InfiniteScroll.tsx：
- Props: loadMore: () => Promise<void>, hasMore: boolean
- 滚动到底部自动触发 loadMore
- 加载中显示 spinner
- 用 IntersectionObserver 实现（不用 scroll 事件监听，性能更好）
- 支持自定义 threshold 和 rootMargin

# 例子 3：API 路由
创建 src/app/api/webhook/stripe/route.ts：
- POST 接口，接收 Stripe webhook 事件
- 验证 Stripe 签名（从环境变量读 webhook secret）
- 处理 checkout.session.completed 事件：更新订单状态
- 其他事件类型记录日志并返回 200
- 返回标准格式 { code: number, data?: any, message: string }

# 例子 4：数据库迁移
创建一个 Prisma 迁移：在 User 表上加 lastLoginAt 和 loginCount 字段，
不要改已有字段，不要删除数据。

# 例子 5：测试文件（配合 vitest）
给 src/utils/retry.ts 写测试：
- 第一次成功 → 不重试
- 失败两次后成功 → 重试 2 次
- 全部失败 → 跑满 maxRetries，最终抛错
- 每次重试间隔递增

三种编码模式（含选择策略）

模式何时用例子
直接写小函数、工具类、没有歧义的需求「写一个 deepClone 函数」
先讨论再写有技术选型需要权衡「我要做文件上传——用 AWS S3 还是 Cloudflare R2？先分析利弊」
Plan 模式涉及多个文件、多个模块`/plan 用户邀请系统` → Claude 先出方案

高阶技巧：让 Claude 给出多个方案

实现一个搜索功能，给我三个方案：
1. 最简单的（5分钟搞定）
2. 最完整的（生产就绪）
3. 你最推荐的一个（平衡速度和质量）
每个方案列清楚：用什么库、改哪些文件、优缺点

这样你先看菜单再点菜，而不是直接吃了一盘你不想要的东西。

让 Claude 自我迭代

刚写的这个函数：
1. 自己审查一遍，有没有边界条件没处理？
2. 能不能减少时间复杂度？
3. TypeScript 类型够不够严格？（不要用 any）
4. 重新写一遍，重点提高可读性

Claude 通常能在第二步发现自己的问题——比如忘了处理 null、类型不够精确、缓存可以加。

实战：让 Claude 写一个完整的 CRUD 模块

我要给项目加一个「标签管理」模块。按这个顺序来：

第 1 步：先给我列出需要创建/修改的文件清单，等我确认。
第 2 步：创建数据模型（Prisma schema）。
第 3 步：写 API 路由（RESTful，4 个接口）。
第 4 步：写输入校验（zod schema）。
第 5 步：写单元测试。
第 6 步：代码审查（你自己审查自己的代码）。

每一步我确认后再做下一步。

常见踩坑

坑 1：Claude 的 import 顺序乱了

修复：在 CLAUDE.md 里加「import 按以下顺序排列：第三方库 → 内部模块 → 类型 → 样式」

坑 2：Claude 编造了一个不存在的 API

你让它写前端组件调用 /api/user/profile，但这个接口还不存在。修复：先让它写 API 再写前端，或者明确说「这个接口已经存在，调用方式是这样……」

坑 3：类型定义不严格

Claude 有时候会用 any 或 Record 偷懒。修复：在 prompt 里加「禁止使用 any 类型」或放 CLAUDE.md 里。

今天的小练习

  1. 找一个函数，让 Claude 改参数签名并更新所有调用处
  2. 让 Claude 用「三个方案」模式帮你设计一个新功能
  3. 让它写完代码后自我审查并优化
  4. 故意给它一个模糊需求，看它怎么回应——然后给精确需求，对比输出质量

今日小结： 好需求 = 精确位置 + 明确接口 + 验收标准 + 技术选型。写代码不只是「让它写」，而是「设计→实现→自我审查→你审核」的完整链路。

第 4 天 · 多文件编辑：重构、重命名与批量操作

5月12日 周一Day 4/15

单文件编辑只是热身。真正的开发工作里，改一个需求通常要动 5 个文件——模型定义、服务层、API 路由、类型文件、测试。今天学的是怎么让 Claude 一次性、干净地处理跨多个文件的编辑。

全局重命名：不只是查找替换

全局重命名最怕的就是看起来改了，实际上漏了——或者改错了不该改的东西。Claude 能处理语义级别的重命名，而不是文本匹配。

# 基础：函数重命名
把整个项目里 
- getAllUsers 重命名为 listUsers
- updateUserProfile 重命名为 updateProfile
确保：
1. 所有 .ts / .tsx 文件里的调用都更新
2. 测试文件里的 mock 和断言也更新
3. 文档和注释里的引用也更新
4. package.json 里的 scripts 如果有引用也更新

实战：组件重命名 + 路径迁移

src/components/common/Button.tsx 改成 src/components/ui/PrimaryButton.tsx。
操作：
1. 移动文件到新位置
2. 更新组件名和 export
3. 找到所有 import 了这个组件的地方，更新 import 路径
4. Storybook stories 文件如果有也要更新
5. 完成后运行 tsc --noEmit 确保没有类型错误

坑：Claude 改了 node_modules 里的东西

Claude 不会被 .gitignore 限制，如果你说「整个项目里」，它可能真的扫进 node_modules。所以永远指定范围：

只改 src/ 目录下的文件，不要碰 node_modules/、dist/、.next/

文件拆分：600 行 → 3 个文件

单文件长到几百行的时候，维护成本骤升。Claude 能帮你做外科手术式的拆分。

拆分前：src/services/orderService.ts —— 600 行

这个文件 src/services/orderService.ts 有 600 行，
包含三个职责：订单创建、订单支付、订单通知。

帮我拆成三个文件：
1. src/services/order/orderCreate.ts 
   - 所有创建订单相关的函数：validateOrder、calculateTotal、createOrderRecord
2. src/services/order/orderPayment.ts
   - 支付相关：processPayment、refundPayment、verifyPaymentStatus
3. src/services/order/orderNotify.ts
   - 通知相关：sendOrderConfirmation、notifyShipping

要求：
- 保持一个 index.ts 作为统一入口，重新导出所有函数
- 共享的工具函数抽到 src/services/order/helpers.ts
- 拆分后运行测试，确保全部通过
- 外部调用 orderService 的地方要保持兼容

拆分策略对比

策略适用场景风险
按职责拆分函数自然分组明显低——各组独立性强
按数据类型拆分多种实体混在一个文件中——可能有交叉引用
按依赖方向拆分有明确的内/外层依赖中——要小心循环依赖

拆分后让 Claude 验证：

拆分完成。现在帮我：
1. 检查有没有循环依赖
2. 运行 madge 或手动分析导入关系
3. 确认所有旧的 import 路径都能正确解析

批量生成：一套模板，多个文件

Step-by-Step（分步）

适合：不确定性高、每个文件改动不同、想边改边审

Step-by-Step 的优势： 每一步都能 review diff，发现问题立即刹车，不会亡羊补牢。

CLAUDE.md 是什么

## Stack
- Frontend: Next.js 14 (App Router), TypeScript, Tailwind CSS, shadcn/ui
- Backend: Next.js API routes, Prisma ORM, PostgreSQL 16
- Auth: NextAuth.js v5 with GitHub + Google OAuth

- Email: Resend
- Testing: Vitest (unit), Playwright (E2E)
- Package manager: pnpm (不要用 npm 或 yarn)

## Architecture
- `src/app/` — Next.js App Router pages and API routes
- `src/components/` — React components, 按功能分组
- `src/lib/` — 纯工具函数，不能依赖 React 或数据库
- `src/services/` — 业务逻辑层，可依赖数据库，但不能依赖 HTTP 请求对象
- `src/db/` — Prisma schema 和数据库工具

## Code Conventions

### TypeScript
- 禁止使用 `any`，如果必须用，用 `unknown` 加类型守卫
- 类型导入使用 `import type`
- Props 使用 `type` 而不是 `interface`（除非需要 extends）
- 导出函数必须显式标注返回类型

### Naming
- React 组件：PascalCase，文件名和组件名一致
- 函数/变量：camelCase
- 数据库字段：snake_case
- API 路由：kebab-case
- 常量：UPPER_SNAKE_CASE

### Import Order（自动排序，不要手调）
1. React/Next.js 相关
2. 第三方库
3. 内部模块（@/ 别名）
4. 类型导入
5. 样式/资源

### Error Handling
- API 路由永远有 try-catch，返回 { code, data, message } 格式
- 不要在 catch 里吞掉错误——至少 console.error
- 用户可见的错误消息用中文，开发者日志用英文

## Git Workflow
- Commit message: Conventional Commits (feat/fix/refactor/docs/chore)
- 分支命名: feature/xxx, fix/xxx, chore/xxx
- 不要在 commit 里包含 secrets

## Testing
- 写测试文件放在 `__tests__` 目录下，与被测文件同级
- 使用 describe/it 结构，测试名用中文描述场景
- 覆盖：正常路径、边界条件、错误路径、并发场景

## Rules for Claude
- 修改代码前先说计划（除非是很小的改动）
- 只改我明确指定的文件，不要顺手优化其他文件
- 新依赖要先问，不要直接 npm install
- 不要生成多余的注释（代码自解释）, 但复杂逻辑要加为什么这样做的注释

- 检查是否加了鉴权（除非路由名包含 public）

### 当修改数据库相关代码时

第 8 天 · 任务规划：用 /plan 把复杂需求变成可执行方案

/plan 模式详解

输入 /plan 后，Claude 会进入规划模式。它不会再改代码，而是分析需求、阅读相关代码、输出一个结构化的执行计划。

基本用法：

/plan 我需要给订单系统加一个「部分退款」功能。
目前只支持全额退款。

要考虑：
- 一个订单可以多次部分退款
- 退款总额不能超过订单总额
- 退款需要经过审批（金额超过 500 元需要管理员审批）
- 退款状态需要实时同步到前端

Claude 会输出类似这样的计划（大幅简化版）：

## Plan: 部分退款功能

### 1. 数据模型变更
- 修改 Order 表：新增 refundableAmount 字段
- 新建 RefundRequest 表：amount, reason, status, approverId
- 新建 RefundApproval 表：requestId, approverId, decision, comment

### 2. API 变更
- POST /api/orders/:id/refund — 创建退款申请
- GET /api/orders/:id/refunds — 查询退款历史
- POST /api/refunds/:id/approve — 审批退款
- WebSocket 事件：refund:status_changed

### 3. 前端变更
- 修改 OrderDetail 页面：退款按钮改为「申请退款」

- 审批中不可重复申请
- 退款成功后释放库存

### 5. 测试

### 预估工作量
- 数据模型：30 分钟

- 前端：1.5 小时
- 测试：1 小时
- 总计：约 4 小时

手动任务分解：5 轮推进法

/plan 给的是计划，真正干活是按轮次推进。这是经过验证的高效模式：

第 1 轮：定义边界

1. 分析现有代码中与用户、内容相关的模块

3. 列出所有需要明确的决策点（比如：收藏的是文章还是商品？要不要分类？）

第 2 轮：数据建模

基于第 1 轮的清单。帮我设计数据模型：
- Prisma schema 改动
- 字段类型、关系、索引
- 迁移策略（是否影响现有数据）

第 3 轮：API 设计

基于第 2 轮的模型。设计 API：
- 接口列表和路由
- 请求/响应格式
- 错误处理
- 鉴权策略

第 4 轮：逐步实现

按顺序实现：
1. 先改数据模型
2. 再写 API
3. 接着写前端
4. 最后写测试

每一步我确认后再继续。

1. 代码质量：命名、结构、重复逻辑
2. 安全性：鉴权、输入校验、注入风险
3. 性能：N+1 查询、无索引查询
4. 测试覆盖：关键路径都有测试吗

第 10 天 · Hooks 自动化：打造你的安全网和工作流

5月20日 周三Day 10/15

Hooks 是 Claude Code 的事件系统——在特定时刻自动触发脚本。你可以把它理解为 Claude Code 的「if this then that」：文件被修改了 → 自动格式化；要执行危险命令 → 弹窗确认。今天学会配置，你的工作流会自动运转。

四种 Hook 事件类型

事件触发时机典型用途
`PreToolUse`Claude 准备调用某个工具之前拦截危险操作、注入检查逻辑
`PostToolUse`Claude 调用某个工具之后自动格式化、运行 lint、提交后通知
`Notification`Claude 发送通知时桌面通知、Slack 消息
`Stop`Claude 响应完成时自动运行测试、检查文件状态

实战 Hook 2：安全守卫（PreToolUse）

在你最关心的操作上设置关卡：

// .claude/hooks/confirm-dangerous.js
const command = process.env.CLAUDE_TOOL_INPUT_COMMAND || '';

const dangerous = [
  { pattern: /rm\s+-rf/, reason: '递归强制删除' },
  { pattern: /git\s+push\s+.*--force/, reason: '强制推送' },
  { pattern: /DROP\s+(TABLE|DATABASE)/i, reason: '数据库删除操作' },
  { pattern: /curl.*\|\s*bash/, reason: '管道执行远程脚本' },
  { pattern: /chmod\s+777/, reason: '过度开放权限' },
  { pattern: /npm\s+unpublish/, reason: '取消发布 npm 包' },
];

const match = dangerous.find(d => d.pattern.test(command));

if (match) {
  console.error(`⚠️  [安全守卫] 检测到危险操作: ${match.reason}`);
  console.error(`   命令: ${command}`);
  console.error(`   此操作已被阻止。如果确实需要执行，请手动在终端运行。`);
  process.exit(2); // 退出码 2：阻止执行
}

process.exit(0);

Exit Code 说明

Hook 脚本的退出码决定 Claude 的行为：

退出码含义Claude 的行为
0成功继续执行操作
1一般错误向用户报告错误，但继续
2阻止不执行该操作，并告知用户原因

坑：exit code 2 只对 PreToolUse 有效。 在 PostToolUse 里 exit 2，操作已经执行了，阻止不了。

    自建 MCP Server（概念概述）

    MCP Server 本质是一个实现了标准接口的本地进程。最小的 MCP Server 就几十行代码：

    // 概念示意：一个简单的天气 MCP Server
import { Server } from "@anthropic/mcp-sdk";

const server = new Server({
  name: "weather-mcp",
  version: "1.0.0"
});

server.addTool({
  name: "get_weather",
  description: "获取指定城市的当前天气",
  parameters: {
    type: "object",
    properties: {
      city: { type: "string", description: "城市名，如 Beijing" }
    },
    required: ["city"]
  },
  handler: async ({ city }) => {
    // 调天气 API
    const weather = await fetchWeather(city);
    return {
      temperature: weather.temp,
      condition: weather.description,
      humidity: weather.humidity
    };
  }

精细化规则：DO/DON'T 模式

模糊的规则没用，精确的规则才是好规则：

## 规则（按精确度排序）

### ❌ 模糊（几乎没用）
- 写干净的代码

### ⚠️ 半模糊（有一点用）
- 变量名要有意义

### ✅ 精确（真正有用）

#### DO
- 数据库模型用 snake_case 字段名
- API 响应用 camelCase（通过 Prisma 序列化转换）
- 异步函数命名以动词开头：fetchXxx, createXxx, updateXxx, deleteXxx
- 超过 3 个参数的函数用对象参数
- 涉及金额的计算用整数（分）而不是浮点数

#### DON'T
- 不要在组件里直接调 fetch——封装到 service 层
- 不要在循环里执行数据库查询
- 不要用 `as` 做类型断言（除非有类型守卫在前）
- 不要在 catch 里吞掉错误不处理
- 不要引入超过 50KB 的新依赖（除非必需）

验证规则是否有效的方法： 如果规则写成「Claude 应该……」，这是愿望。写成「用 X」「不要用 Y」，这是规则。

工作流定义

CLAUDE.md 不只是规则列表——你可以定义完整的工作流：

## 工作流：新增 API 接口

当我要求新增一个 API 接口时，按以下步骤执行：

1. **类型定义**
   - 在 src/types/api.ts 里定义请求和响应的 TypeScript 类型
   - 导出类型供前端使用

2. **Zod Schema**
   - 在 src/schemas/ 下创建对应的 zod schema
   - Schema 名和类型名对应：CreateUserRequest → createUserSchema

3. **Service 层**
   - 在 src/services/ 下实现业务逻辑
   - 不依赖 HTTP 请求对象（纯函数或依赖注入数据库客户端）

4. **API 路由**
   - 在 src/app/api/ 下创建路由文件
   - 使用 zod schema 校验输入
   - 调用 service 层
   - 返回统一格式 { code, data, message }

5. **测试**
   - Service 层单元测试：正常 + 异常 + 边界
   - API 层集成测试：HTTP 请求模拟

6. **文档**
   - 如果接口是给前端用的，更新 API 文档（OpenAPI 注释）

第 13 天 · 会话管理与成本控制

5月26日 周二Day 13/15

Claude Code 按 token 计费。不管理会话，你就不知道钱花哪了；不控制成本，月底账单会让你想把电脑合上。今天把会话的生命周期和成本优化全部讲清楚。

会话生命周期

一个 Claude Code 会话从启动到关闭经历了什么：

启动 claude
  ↓ 读取 CLAUDE.md、项目结构（一次性 token 开销）
  ↓
第 1 轮对话
  ↓ Claude 处理：读文件 + 思考 + 写回复
  ↓
第 2 轮对话
  ↓ 上下文 = CLAUDE.md + 第 1 轮完整内容 + 第 2 轮你的输入
  ↓
第 N 轮对话
  ↓ 上下文越来越长，token 消耗越来越大
  ↓
关闭会话 / 执行 /compact 或 /clear

关键洞察：第 10 轮的 token 消耗通常比第 1 轮高 3-5 倍，因为历史对话全部在上下文里。

/compact vs /clear：选对策略

操作效果什么时候用
`/compact`Claude 把对话历史压缩成摘要，释放空间对话很长但后续任务还需要之前的背景
`/clear`清空全部对话历史新任务完全不相关，旧上下文会干扰
新会话重新启动 claude`/clear` 还不够——想要全新的 CLAUDE.md 加载

最佳实践：

# 你的 Claude Code 会话管理策略

1. 每个功能/任务一个会话（不要一个会话做所有事）
2. 超过 30 轮对话 → /compact
3. 换新任务 → /clear
4. 一天开始 → 新会话（确保读取最新的 CLAUDE.md）
5. 用 /cost 定期检查，单次会话超过 $2 时警惕

成本构成分析

Claude Code 的成本来自几个部分：

成本来源占比（典型）说明
上下文加载~10-15%CLAUDE.md、文件读取、对话历史
你的输入~5%你的 prompt
Claude 的输出~20-25%生成的代码、解释、回复
工具调用结果~50-60%文件内容、命令输出、搜索结果

最大的隐性成本：工具调用返回的内容。 你让 Claude 读了一个 2000 行的文件，这 2000 行全部作为 token 计费——不管 Claude 只看了其中 50 行。

实战设定

  • 项目：Next.js 14 + TypeScript + Prisma + PostgreSQL + Tailwind CSS
  • 已有模块：用户系统（NextAuth）、商品模块（列表 + 详情）
  • 新功能：用户可以把商品加入收藏，查看收藏列表，取消收藏
  • 约束：收藏数据需要记录收藏时的价格（用于后续价格波动分析）

    • 第 1 轮：需求分析与方案设计

    /plan 我要给项目加一个「商品收藏」功能。

      实战中遇到的常见坑

      坑为什么怎么避免
      Claude 在前端代码里 import 了 server-only 的模块没区分服务端/客户端明确说「这是 Client Component，不要 import 服务端模块」
      乐观更新的回滚逻辑漏了Claude 只写了乐观更新，没写 error 回滚在 prompt 里明确「失败时回滚到原状态」
      测试 mock 太深，测的不是真实逻辑Claude 可能用 deep mock 让测试无意义要求「mock 只用于外部依赖（数据库、API），不要 mock 内部函数」
      收藏列表页的 N+1 查询默认查询没 include 关联数据在 Service 层 prompt 里明确「include product 信息，一次查询完成」
      移动端适配被忽略Claude 默认桌面端优先在 CLAUDE.md 里加「默认移动端优先，用 Tailwind responsive class」
