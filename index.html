Day 1

快速上手：十分钟跑起来

5月12日 周二

安装 Claude Code

打开终端，一行命令搞定：

npm install -g @anthropic-ai/claude-code

装完验证：

claude --version

如果没有 Node.js，先去 nodejs.org 下载安装。建议用 nvm 管理版本。

第一次启动

进入你的项目目录：

cd ~/my-project
claude

蓝色的终端界面出现——这就是 Claude Code。没有侧边栏、没有设置面板，就是一个对话窗口。

界面速览

  • 上方：对话历史区域，你和 Claude 的每句话都在这里
  • 下方：输入区，你打字的地方
  • 左上角：显示当前模型和会话 ID
  • Esc 键退出输入模式，用方向键浏览历史

    • 第一个命令

    试试这些简单的开场：

    这个项目是做什么的？
    帮我看看项目结构
    有没有 README？总结一下

    Claude 会自动探索你的项目文件，给你回答。

    两种使用模式

    模式命令适用场景
    交互模式`claude`日常对话、多轮追问
    一次性模式`claude -p "问题"`脚本集成、单次查询

    一次性模式的高级用法

    # 管道输入
cat error.log | claude -p "分析这些错误日志，找出根本原因"

# 结合 shell 操作
git diff HEAD~5 | claude -p "总结这 5 个 commit 的改动，写 release notes"

# 指定模型
claude -p "解释这个函数" --model claude-sonnet-4-20250514

    KEY 配置

    如果还没配 API Key：

    export ANTHROPIC_API_KEY=sk-ant-xxxxx

    写进 ~/.zshrc 一劳永逸。

    常见踩坑

    1. Node 版本太低：Claude Code 需要 Node 18+，node -v 检查
    2. Key 没生效：echo $ANTHROPIC_API_KEY 确认是否输出
    3. 代理问题：国内可能需要设 HTTP_PROXY 环境变量

    今日任务

    装好 Claude Code，进你的项目，问一句「这个项目是做什么的」。你会惊讶它居然真的看懂了。

Day 2

接入国内大模型：省钱又稳定

5月13日 周三

为什么要用国内模型

Anthropic 的 API 直连在国内可能不稳定，而且按 token 收费累积起来不少。国内有不少兼容 OpenAI/Anthropic 格式的模型服务，可以大幅降低成本。

方案一：DeepSeek（推荐首选）

DeepSeek 支持 OpenAI 兼容接口，通过中转或直接配置：

# 方式1：用 opencode 等支持的国内 fork
# opencode 原生支持配置任意 OpenAI-compatible endpoint

# 方式2：环境变量
export ANTHROPIC_BASE_URL=https://your-proxy.com/v1

方案二：LiteLLM 中转

最灵活的方案——用 LiteLLM 在本地搭一个代理，统一管理所有模型：

pip install litellm

# 配置 DeepSeek
litellm --model deepseek/deepseek-chat \
  --api_base https://api.deepseek.com/v1

然后在 Claude Code 里指向本地代理：

export ANTHROPIC_BASE_URL=http://localhost:8000

方案三：One API（国产开源中转）

One API 是国内流行的一站式模型管理工具，支持几乎所有国内模型：

docker run -d -p 3000:3000 \
  -e SQL_DSN="root:123456@tcp(localhost:3306)/oneapi" \
  justsong/one-api

它的优势：

  • 可视化界面管理多个模型 Key
  • 支出统计、用量限制
  • 支持的渠道极多（DeepSeek、通义千问、智谱、Moonshot……）

    • 模型选择策略

    任务类型推荐模型原因
    简单问答、代码解释DeepSeek V3便宜、快
    复杂重构、架构设计Claude Sonnet 4质量最好
    大量文件批量处理DeepSeek V3省成本
    安全审计、代码审查Claude Opus 4最仔细

    黄金法则：80% 的日常任务用便宜模型，关键决策用贵的。

    省钱实操

    # 限制每次对话的 token 预算
claude --max-tokens 8000

# 定期压缩对话上下文（/compact 命令）
# 在对话中输入 /compact，会把历史压缩成摘要

# 避免把整个仓库都丢给它
# 用 @ 只引用需要的文件

Day 5

文档管理与处理：让代码库开口说话

5月18日 周一

读代码不是找文件

Claude Code 的读代码能力强在「理解」而不是「检索」：

代码考古

面对一个你不熟悉的遗留项目：

这个项目是什么？从 git 历史能看到它怎么一步步变成现在这样的吗？
@src/legacy/ 这个目录下的代码还有人在用吗？
搜索全项目找出所有引用它的地方

死亡路径分析

如果这个 API 调用的第三方服务超时了，错误会怎么传播？
最终用户会看到什么？有没有哪一层吞掉了错误？

安全审查

审查 @src/api/ 下所有接口的安全性：
- 哪些接口没有鉴权？
- 有没有 SQL 注入风险？
- 用户输入有没有被校验和清洗？
- 敏感信息是否泄漏到日志里？

数据库与 Schema

@prisma/schema.prisma 画出 ER 图（Mermaid 格式），
标出一对多和多对多关系
分析这个 schema，有没有冗余字段？
有没有应该加索引但没加的地方？

依赖分析

分析 @src/ 下所有模块的依赖关系，
画出依赖图，标出循环依赖
package.json 里有哪些依赖是多余的？
哪些依赖有已知安全漏洞？

配置文件管理

@.env.example @config/ 检查所有环境变量：
哪些没有默认值？哪些没有文档说明？
哪些在不同环境下容易配错？

批量文档生成

给 @src/utils/ 下每个函数生成 JSDoc 注释，
包含参数类型、返回值、使用示例
把 @src/ 的所有 public API 整理成一份索引文档，
按模块分组，每个函数一句话说明

Day 7

个性化工作流：让 Claude 变成你的形状

5月20日 周三

CLAUDE.md：你的项目说明书

在项目根目录创建一个 CLAUDE.md——这是你跟 Claude 之间的「合同」。每次启动 Claude Code，它都会先读这个文件。

基础版 CLAUDE.md

# CLAUDE.md

## 项目概述
这是一个电商后台管理系统，
前端 React + TypeScript，后端 Node.js + Prisma。

## 技术约定
- 所有组件的 props 用 interface 定义
- 状态管理用 Zustand
- API 请求统一用 src/utils/request.ts 里的封装
- 测试用 Vitest，覆盖率要求 70%+

## Commit 规范
- 格式：type(scope): 描述
- type: feat / fix / refactor / docs / test
- 用中文写 commit message

进阶版 CLAUDE.md

## 工作习惯
- 修改代码之前先解释计划，等我说「继续」再动手
- 不要自动创建新文件，除非我明确要求
- 重构时保持 API 兼容，不要改已有的 import 路径

## 代码风格偏好
- 函数优先于类
- 能一行解决的不用三行
- 注释解释「为什么」，不是「是什么」
- 错误处理不要吞异常，必须向上抛或记录日志

## 线上环境规则
- 永远不要修改 production 配置
- 数据库操作只读，除非我明确说「可以写」
- 不要运行 npm publish 或任何部署命令

模板化工作流

把常用的指令保存到 CLAUDE.md：

## 常用工作流

### 代码审查
当我说「review」时，运行以下检查：
1. 安全检查（SQL 注入、XSS、敏感信息）
2. 性能检查（N+1 查询、不必要的循环）
3. 代码风格检查（命名、结构）
4. 测试覆盖检查

### 修复 bug
当我说「fix」时：
1. 先分析根因
2. 给出修复方案（2-3 种）
3. 等我确认后再改代码
4. 加上对应的测试用例

分支策略

用 .gitignore 配合 CLAUDE.md：

## Git 工作流
- 在当前分支工作，不要自动切分支
- push 之前先让我确认
- commit message 用中文，包含 issue 编号

Day 8

提示词优化技巧（上）：问对问题比会写代码重要

5月21日 周四

核心原则

好的提示词不是花哨的模板，而是清晰传递你的意图。

坏 vs 好

坏的提问好的提问
「帮我优化这段代码」「这段代码循环里有数据库查询，帮我把查询提到循环外面」
「这个项目有什么问题」「审查 @src/api/ 的安全性和错误处理」
「写个登录功能」「用 JWT 实现登录，需要 refresh token，参考 @src/auth/ 的现有结构」

四大提示要素

每次提问尽量包含：

  1. 上下文：告诉 Claude 现在在干什么
  2. 输入：用 @ 引用具体的文件或代码
  3. 指令：你要它做什么
  4. 约束：有什么要求

示例：

（上下文）我在重构支付模块，
所有金额现在统一用「分」为单位。

（输入）@src/services/payment.ts

（指令）把所有金额相关的计算从「元」改成「分」，
更新对应的类型定义。

（约束）不要改 API 接口格式，
入参出参仍然用「元」，转换在 service 层做。

角色扮演

给 Claude 一个身份，它会在那个框架下思考：

你是一个有 10 年后端经验的架构师。
审查这个微服务方案有什么隐患。
你是一个刚被 oncall 吵醒的 SRE。
下面的告警日志，最需要先处理什么问题？
你是一个完全不懂技术的新人 PM。
我跟你解释这段代码在做什么，你用白话复述一遍，
确认我讲清楚没有。

分步 vs 一次完成

简单任务可以一次说完。复杂任务要拆：

# 不要这样（太模糊）
帮我重构用户模块

# 这样（分步）
第一步：分析 @src/modules/user/ 的结构，
告诉我有哪些可以优化的地方

# Claude 分析完后
第二步：先重构 services 层，
把业务逻辑从 controller 里抽出来

# 完成后
第三步：更新测试，确保覆盖率不掉

让 Claude 自我审查

改完代码后：

你刚才改了什么？为什么这么改？
有没有更好的方案？
检查你刚才的改动：
有没有引入新的 bug？有没有破坏现有的 API？

这个「二次审查」能抓到很多 Claude 自己疏忽的问题。

今日任务

用「四要素法」和「角色扮演」分别各提一个问题，看看输出质量有没有明显提升。

高级功能：Hooks 和 MCP

5月27日 周三

Hooks：自动化你的工作流

Hooks 是 Claude Code 的自动化机制——在特定事件发生时自动执行操作。

Hook 类型

事件触发时机
PreToolUse工具被调用之前
PostToolUse工具被调用之后
NotificationClaude 发出通知时
UserPromptSubmit用户提交消息时
Stop会话结束时

实用 Hook 示例

// .claude/settings.json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "command": "prettier --write $CLAUDE_FILE_PATH"
      }
    ]
  }
}

这个配置让 Claude 每次编辑或写入文件后自动运行 Prettier 格式化。

高级 Hook：提交前检查

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash(git push*)",
        "command": "npm test && npm run lint"
      }
    ]
  }
}

在 git push 之前自动跑测试和 lint。失败了就阻止 push。

MCP：扩展 Claude 的能力边界

MCP（Model Context Protocol）让 Claude 能连接外部工具和数据源。

配置 MCP Server

// .claude/mcp.json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@anthropic/mcp-server-filesystem", "/path/to/allowed/dir"]
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@anthropic/mcp-server-github"]
    }
  }
}

常用 MCP Server

Server用途
mcp-server-github管理 Issues、PRs、仓库
mcp-server-filesystem安全的文件系统访问
mcp-server-postgres数据库查询（只读）
mcp-server-slackSlack 消息和频道管理
mcp-server-jiraJira 工单管理

MCP 实战：一键发 PR

配置好 GitHub MCP 后：

看看 git diff，写 commit message，push，
然后在 GitHub 上开一个 PR 到 main 分支

Claude 会一步步执行：diff → message → push → create PR。

假设要修复一个 bug：

# 1. 分析问题

# 2. 写复现测试

# CLAUDE.md 中的模板区

1. 复现并定位根因
2. 给出 2-3 种修复方案
3. 等我选择后实现
4. 写回归测试
5. 生成 fix commit
